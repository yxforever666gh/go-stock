# Go-Stock 版本更新与运行一致性需求文档

## 1. 文档信息

- 文档类型：产品与工程需求文档
- 适用范围：Go-Stock 桌面端、本地 Web 服务、前端静态资源、Git 仓库及 Windows 发布流程
- 目标读者：开发、测试、发布和运维人员
- 状态：待实施

## 2. 背景与问题

项目多次出现“代码已经修改、提交或打 tag，但实际运行的仍是旧版本”的情况。根因通常不是代码修改未生效，而是版本发布链路中的多个状态没有同步：

- Git 提交和 tag 已更新，但没有重新构建运行制品。
- 新制品已经生成，但 `runtime/current.json` 仍指向旧制品。
- 发布指针已经更新，但旧进程没有停止，端口仍由旧二进制占用。
- Go 二进制重新编译前没有重新构建前端，导致新二进制内嵌旧的 `frontend/dist`。
- 后端已经运行新版本，但浏览器仍缓存旧入口或旧资源。
- 页面展示的是手工写死的版本号，不能代表真实运行制品。
- tag、当前提交、制品内嵌 commit 和实际运行进程之间缺少强制一致性校验。

因此，版本更新不能只定义为“修改版本号并 push”，而必须覆盖从版本声明到最终运行验证的完整闭环。

## 3. 目标

1. 建立唯一、可审计的版本来源，消除多处手工版本号错位。
2. 保证每次正式发布都对应唯一且不可变的 Git tag 和构建制品。
3. 保证部署完成后，发布指针、进程、制品、commit、tag 和页面展示完全一致。
4. 部署失败时自动恢复到明确的上一版本，并保留失败证据。
5. 用户能够直接在界面和健康检查接口确认当前真正运行的版本。
6. 防止浏览器缓存导致“后端已升级、页面仍像旧版本”的假象。

## 4. 非目标

- 本需求不改变研究、推荐、模拟交易或持仓生命周期规则。
- 本需求不要求每次版本更新都升级数据库 schema。
- 本需求不实现在线差分升级或静默自动更新。
- 本需求不允许通过移动已经正式发布的 tag 覆盖旧版本。

## 5. 核心原则

### 5.1 运行版本是最终事实

是否升级成功，以正在监听服务端口的实际二进制及其 `/readyz` 身份为准，而不是以工作区代码、GitHub 页面或本地 tag 为准。

### 5.2 每次正式变更使用新版本

- 正式发布遵循语义化版本号格式 `MAJOR.MINOR.PATCH`。
- 已经推送或部署的版本 tag 不得移动、覆盖或强制更新。
- 正式版本发布后如需追加修复，必须创建新的 PATCH 版本。

### 5.3 制品不可变

每个制品由版本号和完整 commit 唯一确定，推荐目录结构：

```text
runtime/releases/<version>/<full-commit>/
  go-stock-web.exe
  zoneinfo.zip
  build.json
```

同一版本和 commit 的制品不得被后续构建覆盖。

## 6. 功能需求

### FR-01：版本唯一来源

1. 应以 `internal/releaseinfo/release_manifest.json` 中的 `appVersion` 作为应用版本唯一来源。
2. 后端运行状态、系统信息接口和前端页面必须读取该版本，不得各自写死。
3. 前端 `package.json`、`package-lock.json`、OpenAPI、README、CHANGELOG 和发布说明必须通过一致性测试与发布清单保持同步。
4. 数据库 schema 版本与应用版本分别管理，不得因为 App 版本升级而自动增加 schema 版本。

### FR-02：界面版本展示

1. 底部导航栏 GitHub 图标右侧应展示真实运行版本，例如 `GitHub · v1.7.10`。
2. “关于软件”页面应展示相同版本。
3. 版本值必须从本机运行服务的系统信息接口获取。
4. 开发环境或接口不可用时应显示 `vdev`，不得显示可能误导用户的旧固定版本。

### FR-03：Git tag 门禁

1. 正式构建和部署前必须存在与 `appVersion` 完全同名的 tag。
2. tag 必须指向当前准备构建的完整 commit。
3. tag 不存在、指向其他 commit 或版本格式不合法时，发布流程必须立即失败。
4. 发布完成前必须验证远端 `main` 和远端 tag 均已指向预期 commit。
5. 禁止通过 `--force` 移动已发布 tag。

### FR-04：发布前检查

正式构建前必须依次验证：

1. 发布相关文件不存在未提交改动。
2. 版本一致性测试通过。
3. 后端单元测试、Go vet 和 OpenAPI 合约检查通过。
4. 前端运行时测试、lint 和生产构建通过。
5. 前端生产构建必须先于 Go 二进制构建完成，确保 Go 内嵌的是当前版本静态资源。
6. 已知例外测试必须有明确记录；不得把新增失败伪装成已知失败。

### FR-05：制品身份

构建产物必须内嵌并输出以下信息：

- App 版本号
- 完整 Git commit
- 构建时间
- 二进制 SHA-256
- 工作区是否为 dirty
- 主库 schema 版本
- 分钟库 schema 版本

正式制品的 `dirty` 必须为 `false`。

### FR-06：原子发布指针

1. 当前运行制品统一由 `runtime/current.json` 指定。
2. 指针写入必须采用临时文件加原子替换，不得直接覆盖一半内容。
3. 更新指针前必须保存上一版本回滚凭据。
4. 启动脚本只能启动指针指定的绝对二进制路径，不得从工作区临时编译或猜测最新目录。
5. 停止服务时必须确认被停止进程的可执行路径与旧指针一致。

### FR-07：部署顺序

同 schema 版本发布应按以下顺序执行：

```text
校验新制品
→ 保存旧指针
→ 停止旧进程
→ 原子切换 current.json
→ 启动新进程
→ 精确 readiness 校验
→ 发布完成
```

数据库 schema 升级发布应在停止旧进程后，先执行现有永久归档和迁移流程，再启动新进程。数据库 schema 不变时不得无故执行迁移或创建迁移前归档。

### FR-08：精确 readiness

`/readyz` 至少应返回：

```json
{
  "appVersion": "1.7.10",
  "commit": "<full-commit>",
  "artifactSHA256": "<sha256>",
  "mainSchemaVersion": 12,
  "minuteSchemaVersion": 2,
  "readiness": {
    "migrations": true,
    "database": true,
    "services": true,
    "scheduler": true,
    "ready": true
  }
}
```

发布成功必须同时满足：

1. `/readyz` 版本、commit、哈希和 schema 与 `runtime/current.json` 完全一致。
2. 监听服务端口的进程路径与指针中的二进制绝对路径一致。
3. 指针中的二进制和 zoneinfo 文件哈希与 `build.json` 一致。
4. readiness 所有必要子状态为真。

任一条件不满足，均不得报告“部署成功”。

### FR-09：前端缓存策略

1. HTML 入口文件应使用 `no-cache` 或等效策略，确保浏览器每次重新验证入口。
2. 带内容 hash 的 JS、CSS、字体和图片资源可使用长期不可变缓存。
3. 页面加载后展示的版本必须来自后端接口，而不是静态 HTML 中的固定文本。
4. `/readyz` 已是新版但页面仍显示旧版时，应提供明确的重新加载提示，并记录为前端缓存问题，而不是重复部署。

### FR-10：失败回滚

1. 新进程启动失败或 readiness 超时后，应停止失败进程并恢复旧指针。
2. 仅当旧二进制与当前数据库 schema 兼容时，才允许自动重启旧版本。
3. schema 已升级且旧版本不兼容时，不得盲目启动旧二进制，应使用对应数据库归档和回滚凭据。
4. 回滚失败时必须保留当前指针、上一指针、失败日志和数据库状态，并明确报告人工处理要求。
5. 回滚不得删除或伪造已经产生的业务数据。

### FR-11：发布结果审计

每次发布应记录：

- 版本号和 tag
- commit
- 构建时间
- 制品路径及哈希
- 部署开始和完成时间
- 上一版本回滚凭据
- schema 是否变化
- readiness 校验结果
- 实际进程 PID 和可执行路径
- 发布成功、回滚成功或发布失败状态

日志不得记录密钥、令牌或数据库原始敏感内容。

## 7. 标准发布流程

### 7.1 开发完成

1. 修改代码和测试。
2. 决定新的版本号。
3. 同步版本清单、前端、OpenAPI、README、CHANGELOG 和发布说明。
4. 完成全套验证。

### 7.2 Git 发布

1. 提交发布相关改动。
2. 推送 `main`。
3. 创建与版本号同名的 annotated tag。
4. 推送 tag。
5. 验证远端 `main` 和 tag 指向同一 commit。

### 7.3 构建与部署

1. 从 tag 对应的干净 worktree 构建前端。
2. 构建带 commit、构建时间和 dirty 标志的 Go 二进制。
3. 生成 `build.json` 并核对真实 SHA-256。
4. 执行标准部署命令。
5. 核对 `/readyz`、进程路径和 `runtime/current.json`。
6. 使用真实浏览器确认页面展示新版本。
7. 清理临时 worktree，但保留不可变制品和发布凭据。

## 8. 验收标准

### AC-01：正常升级

给定当前运行 1.7.9，当发布 1.7.10 后：

- 远端 `main` 和 `1.7.10` tag 指向同一 commit。
- `runtime/current.json` 指向 1.7.10 制品。
- 实际监听进程路径属于 1.7.10 制品目录。
- `/readyz` 返回 1.7.10、预期 commit 和预期哈希。
- 页面显示 `GitHub · v1.7.10`。

### AC-02：只更新代码但未构建

当工作区代码已修改但没有新制品时，运行版本保持不变，并且系统不得错误显示新版本。

### AC-03：tag 错位

当版本 tag 不存在或指向其他 commit 时，构建和部署均被拒绝，当前服务不受影响。

### AC-04：旧进程占用端口

当端口仍由非指针进程占用时，启动必须失败并报告实际 PID 和路径，不得把旧进程判断为新版本 readiness 成功。

### AC-05：前端缓存

当后端已是新版而浏览器入口缓存未更新时，重新验证入口后必须加载带新 hash 的资源，并显示后端真实版本。

### AC-06：启动失败回滚

当新二进制启动失败时，系统恢复旧指针和兼容的旧进程；发布结果明确标记为回滚，不得标记为成功。

### AC-07：数据库版本不变

当 App 版本升级但 schema 不变时，不新增迁移记录、不创建无意义的迁移前数据库归档，业务数据保持不变。

## 9. 测试计划

1. 版本一致性单元测试：清单、前端、OpenAPI、README 和 CHANGELOG 一致。
2. tag 门禁测试：缺失 tag、错指 tag、正确 tag 三种情况。
3. 制品身份测试：内嵌 commit、版本、构建时间、dirty 和 SHA-256。
4. 指针原子写入与损坏恢复测试。
5. 旧进程占用端口和进程路径错位测试。
6. readiness 字段缺失、值错位和超时测试。
7. 同 schema 部署测试和 schema 升级部署测试。
8. 新进程启动失败及自动回滚测试。
9. 前端版本标签的运行时测试和真实浏览器渲染检查。
10. HTML 与 hash 静态资源缓存头检查。

## 10. 运维排查顺序

发现“运行的还是旧版本”时，应按以下顺序排查：

1. 查看 `/readyz` 的版本、commit 和制品哈希。
2. 查看 `runtime/current.json`。
3. 查看监听端口对应进程的绝对可执行路径。
4. 核对 `build.json` 与真实文件哈希。
5. 核对本地及远端 tag 指向。
6. 若后端身份一致但页面仍旧，检查 HTML 缓存和浏览器资源请求。
7. 禁止在身份未核对前反复重启、重新迁移或移动 tag。

## 11. 发布完成定义

只有同时满足以下条件，版本更新任务才算完成：

- 代码、测试和版本文件已提交。
- `main` 与不可变版本 tag 已推送。
- 干净制品构建完成且哈希可验证。
- 当前指针和实际进程均指向该制品。
- `/readyz` 精确一致且 ready 为真。
- 页面展示真实新版本。
- 临时构建目录已清理。
- 无关工作区改动保持原样。
